## 學習路徑

每個單元都先回答實際問題，再閱讀符號、tensor 維度與對應程式，最後用小數值例子檢查理解。完整推導留待成果完成後補學。

| 次序 | 內容與實作接點 | 完成標準與留下的筆記 |
|---|---|---|
| 1 | PyTorch tensor、batch、device、autograd、optimizer、train/eval、checkpoint；用小型分類問題練習 | 能修改模型並完成訓練、驗證與恢復；能解釋一次更新，以及梯度計算和 train/eval 的差別 |
| 2 | 示範資料與行為複製：觀測、任務條件到低階鍵鼠動作；資料切分、分類 loss、mask | 能追蹤一筆資料從錄製證據到模型視圖，指出輸入、標籤、維度與避免洩漏的方法 |
| 3 | 畫面編碼器、latent tokens、解碼器、重建 loss | 能解釋小型 UI 資訊遺失的影響，並讀懂重建圖與關鍵項目辨識結果 |
| 4 | 世界動態模型、歷史 context、動作條件、自由預測與 shortcut 方法 | 能區分訓練與推理資料流，解釋預測步數增加時的誤差，以及動作診斷基準的用途 |
| 5 | 任務條件 policy/reward 微調、value、return、imagination 與策略更新 | 能用表格指出三階段的輸入、目標、loss、更新與凍結參數，並說明模型誤差如何影響策略 |
| 6 | 品質 gate、離線與閉迴路評估、原始計數、信賴區間、失敗分析 | 能從原始證據解釋圖表，分清規劃、實測、驗收與研究結論 |

第一單元先預留半天至一天作為估計，依練習結果調整。後續各單元跟著實作進度學習，不要求先讀完所有理論才開始工作。正式訓練順序仍沿用既定三階段課程；先學行為複製不表示正式訓練跳過世界模型。

每個核心公式附一張筆記：它解決的問題、各符號與維度、資料來源、哪些參數收到梯度、程式位置、小例子。至少能解釋專題實際使用的目標與更新流程；不以背誦推導作為第一輪完成條件。

## 執行與寫作順序

1. 規劃地圖完成後，優先依下一節完成正式錄製器與最小離線驗收流程，再開始首批示範。PyTorch 練習安排在不需使用者操作遊戲的開發時段；它不是錄製器開發的前置條件。同時建立報告空白章節及證據索引。學習與實作工時獨立記錄。
2. 首批約 3 小時示範後，另排 2–4 小時檢查資料有效性與任務覆蓋，依既定規則整理補錄優先序。剩餘約 7 小時依缺口補錄，完成後另排 2–4 小時驗收、編譯與凍結資料。這兩段檢查不代表模型人工判讀已恢復，也不保證其他評分工具全部完成。人工錄製工時不是有效資料時數。
3. 完整資料版本與 split 凍結後，依各階段 gate 推進正式訓練。夜間訓練時關閉 DSP；白天安排錄製、評估、資料檢查與寫作，避免與 GPU 訓練衝突。
4. GPU 工作總預算 32 小時包含除錯、失敗重跑、驗證與儲存，不自動延長，也不保證收斂。人工判讀目前暫緩；所依賴的重建或預測 gate 保持待驗證，後續正式階段不得越過。可持續整理工具、方法章與已取得證據。
5. 依 2026/9/6 使用者指示，取消 9/10 模型凍結與 9/13 成果完成的日期約束，改按實際驗收進度盡快推進。日期放寬不自動改動既有 32 小時 GPU 首輪預算、約 10 小時人工示範投入、30 分鐘回合上限或品質 gate；如需改變這些實驗條件，另外明確修訂。
6. 合格候選依既定 development manifests 選模，再由選定模型執行正式評估。兩候選各 10 回合加最終 30 個有效回合，回合運行最多合計 25 小時，載入與無效重跑另計。只有一個合格候選時不強行湊比較。
7. 每次執行當天更新證據索引。方法與評估協定先寫；結果、討論與摘要依實測補入。最後保留時間核對所有數字來源、整理簡報與練習口試。

## 正式錄製前的工作與工時

以下為 2026/9/5 根據原型程式與決議所做的工程估計，尚非實測工時。估計前提是由 agent 沿用已驗證的 C# 掛點、游標合成及檢查方法製作正式版，使用者負責實機操作與回饋；不要求使用者先自學 C# 才開始。若改成由使用者逐段學習並親自實作，需重新估時。

原型的 20 Hz 效能測試約 69 秒，完整十六項微任務錄製約 432 秒但使用 1 Hz；兩份證據不能合併宣稱已完成 20 Hz 全流程長時間驗收。原型使用單一 `frames.rgba` 與自己的 NDJSON 格式，並非正式資料契約，不能只改頻率就投入大量錄製。

### 到可開始首批 3 小時錄製

工時指單一路線的有效工程及整合測試時數，含 agent 實作與使用者參與的驗收時段，同時工作只計一次。它不是全部由使用者手寫程式的時數，也不是可直接視為連續運行的日曆時間。以每天約 8–10 小時有效工作作排程假設，不將「整天可投入」換算成每天 16 小時。

| 順序 | 工作與完成條件 | 估計時數 |
|---|---|---:|
| A | 盤點原型與正式契約差異，固定正式專案、建置／部署方式、測試用基準場景及輸出位置；建立可逐項檢查的欄位清單 | 2–3 |
| B | 移植畫面、游標、DSP-consumed input 與事件掛點，補齊 scan-code identity、狀態旗標、時間與序號；錄製維持 20 Hz，驗證原始輸入未被模型 catalog 提前丟棄 | 3–5 |
| C | 正式生命週期與標註依據：session／attempt／episode ID、基準場景 fingerprint、擾動與起點、final observation、結果及有效性；核對權威微任務圖所需狀態與事件，不把原型 verifier 直接當 task catalog | 4–6 |
| D | 可輪替 frame chunks、append-only records、manifest、版本與 checksum；移植已驗證的 FFV1 分段、停止後合併、完整核對與暫存清理流程，補齊停止／崩潰後 incomplete 標記及合法前綴保留，量測磁碟空間、持續寫入與編譯讀寫 | 7–12 |
| E | 最小正式離線編譯及檢查路徑：區間對齊、動作聚合與 unsupported／ambiguous masks、completion／task／reward、Zarr／Parquet 輸出、COMPLETED marker、版本與完整性拒絕規則；產出逐回合及逐任務覆蓋表，抽樣驗證 10 Hz 模型視圖的動作聚合 | 6–9 |
| F | 實機端到端驗收與操作說明：完整流程、停止再開、世界重載、失焦、缺幀與截斷檔案；檢查輸出、編譯結果及證據索引，記下開始、停止與失敗處理步驟 | 3–4 |
| G | 專用除錯及重測緩衝，處理前述工作暴露的整合問題；未使用的緩衝可直接留給後續工作 | 5–8 |
| **合計** | **通過驗收後可開始首批正式示範錄製** | **30–47** |

A–F 的一般實作與首次測試合計 25–39 小時；G 為另列的返工緩衝。E 只完成及早檢查資料是否可用的最小正式路徑，不包含完整訓練 loader、全部 sequence sampling／loss masks、模型訓練程式或模型品質 gate 工具。這些仍需在正式訓練前完成並另估工時，不得因 E 完成就宣稱已可正式訓練。

2026/9/6 排程修訂：以上範圍保留為初始估計，不作最低工時或期限。以 A–F 的低端約 25 小時作為順利重用時的工作目標，G 只在實際返工時使用，不預先花完。D 已依儲存決議修訂為 7–12 小時，已完成的原型不重複計入。

加快方式：先完成一個回合從錄製到編譯及讀回，再擴充生命週期與失敗情境；同一組驗收資料重用於畫面、標註、存檔與編譯檢查。證據欄位凍結後，使用者錄製時可穿插不干擾遊戲的 CPU 端資料工具及報告工作。已驗收版本持續錄製時，不熱換錄製器或修改其契約；需要改原始欄位就先停錄。模型、完整 loader 與美化圖表不阻擋已滿足錄製驗收的首批資料。並行只計實際可重疊時段，不預設有人可同時試玩與學習，也不預設磁碟或 CPU 壓縮工作不會影響 DSP。

使用者在 A–F 中預留約 2–4 小時配合環境確認、試玩與原始畫面核對，已包含在表內，不另加一次；除錯重測若需再次試玩，使用 G。這些是錄製器驗收，不是已暫緩的模型重建／預測人工評分。本次僅排程，實際測試在正式實作時執行。

### 開始大量錄製的驗收檢查點

以下是本草案新增的錄製器驗收安排，不改動已定義的模型 gate：

- 用正式設定在 20 Hz 連續錄製至少 30 分鐘，安排至少三個完整基準流程及世界重載。沿用原型擷取性能底線，掉幀率低於 1%、有效寫入率至少為設定值的 95%、GPU readback error 與 writer backpressure 為零；所有 gap 必須明記，sequence 不可跨越。正式版需留存新的驗收證據。
- 在各完整流程核對權威微任務圖的 completion、active task 與 reward，涵蓋非 active 預先完成及等待情境。檢查重設、終止 final observation 與成功／無效的獨立判定。
- 執行 action catalog 已指定的合法、unsupported 與禁止組合測試；操作錄製控制快捷鍵造成的邊界必須保留原始證據並正確遮罩。
- 以專用測試錄製驗證失焦、停止、故障及檔案截斷處理，確保失敗不被當成完整有效 artifact。用同一份 evidence 重編譯時，語意結果一致且來源可追溯。
- 從 evidence 經 compiler 到最小模型視圖抽樣讀回，確認畫面、游標、時間、動作及標註。人工示範應記為示範來源，不能因動作由人輸入就套用自主評估的人工介入失效規則。
- 固定 recorder evidence schema 與必要狀態欄位後才開始首批錄製。未來若僅修改可由完整 evidence 重算的 compiler 規則，產生新 artifact；若缺少原始欄位，相關資料可能必須重錄，不能事後推測補值。

此檢查點不要求先完成模型推理、imagination、完整自主閉迴路控制器或 DSP 與模型同時運作的推理資源 gate。錄製模式須完整保留人類輸入；自主模式日後仍採既定 10 Hz／100 ms deadline。兩者的驗收證據分開。

### 已確認的無損儲存與容量規劃

儲存決策的唯一權威是[驗證原始錄製資料的無損儲存方案之決議](https://github.com/JayWu07291/DSP_Dreamer/issues/11#issuecomment-5565241983)，參數與完整限制見該票連結的 PROPOSAL。本文件僅整理報告與排程需要的重點。

採 FFV1／Matroska，游標合成後 640×360 RGBA 逐幀可逆，包含 alpha。錄製期間每 200 個成功畫面暫存一段；停止後自動合併為 recording.mkv，另有 events.ndjson、frames.ndjson、manifest.json。完整解碼與 hash、幀數、順序、索引及 checksum 通過後才發布完成 manifest，並清理本次清單內 hash 相符的暫存。失敗保留資料並允許重試，既有實驗 evidence 不批次改寫或刪除。

影片採成功畫面的連續播放時間軸，原始 capture ID、request monotonic ticks／frequency、game tick、gap、游標及全域 sequence_number 另存。影片播放 PTS 不作原始時間，最終索引採全片 ordinal。Compiler 依序解碼成既定 Zarr／Parquet，模型仍讀 compiled dataset。

報告可引用相同 1,233 幀候選對照、30 分鐘 20 Hz FFV1 實機、raw 對照、RAM 及啟動修正、自動合併核對清理證據。30 分鐘影像比同幀數 raw 少約 72.1%，僅代表該次工作負載；最新 1,199 幀自動 run 完整核對成功，不冒充正式版長程測試。

容量採用儲存票確認的規劃值：

- 壓縮 evidence 暫留 23 GiB／capture 小時。
- 錄製合併期間另留約一份本次錄製容量與餘裕。
- Compiled RGB 按未壓縮形狀暫留 46.35 GiB／capture 小時，tables／metadata 2 GiB／小時，compiler scratch 1 GiB。
- 初次建立預算約 `71.35 × capture 小時 + 1 GiB`，另加既有資料；合併若與編譯重疊，再計合併暫存峰值。保留舊 dataset 重編譯時另加其容量。
- 上述是規劃值，不是正式 compiler 已實測的大小。以正式 benchmark 校正，容量不足停止新增工作；capture 時數不等於人工示範工時。

正式版仍需完成全域 sequence_number、串流 metadata、長程／冷啟動／故障及 compiler 驗收，受控中斷測試不等於斷電安全。這些安排在 D、E、F 與緩衝內；格式選擇已完成，不重做整場選型。

首批 3 小時採分段錄製，每個回合結束立即執行輕量完整性檢查；遇到缺欄位或系統故障就暫停並修正。首批後另用 2–4 小時進行完整覆蓋檢查與補錄排序。剩餘約 7 小時依缺口安排，既定正常／恢復操作工時比例沿用訓練決議。補錄後再用 2–4 小時完成資料驗收、編譯與版本凍結。

### 接回整體時程

| 里程碑 | 從正式實作起算的累計有效時數 | 排程意義 |
|---|---:|---|
| 錄製器與最小離線路徑通過驗收 | 30–47 | 約第 3–6 個工作日可開始首批錄製 |
| 首批 3 小時錄製及檢查完成 | 35–54 | 可依實測缺口決定補錄內容 |

上述天數以每天 8–10 小時換算並向上取整，只作排程範圍。PyTorch 基礎練習另估 4–8 小時；只有在不需要配合 agent 驗收、且不爭用 DSP 或 GPU 的時段才可穿插，無法穿插就另加時間，不默認全部重疊。

2026/9/6 起不再綁定確切完成日期。上表保留包含緩衝的初估供追蹤；順利重用時以較低工時推進，提前通過驗收就提前錄製。資料凍結後仍有正式模型與評估工具整合、最多 32 小時 GPU 工作、模型 gate、開發與正式評估、報告及簡報收尾。實際完成日期隨里程碑更新，儲存容量與工程工時已承接無損儲存決議，正式整合後再校正。

每天記錄已用工時、驗收結果與剩餘估計。47 小時不是停止開發的上限，超出時更新估計並繼續解決必需項；缺少正式錄製必需的證據時，不投入整批示範。人工模型判讀暫緩仍是後續訓練的獨立阻擋條件；挪出開發時間不代表解除該條件。

## 證據索引與呈現規則

每項研究主張對應一列：主張、資料／checkpoint／工具版本、split 或 manifest、指標、原始計數與分母、門檻、執行狀態、驗收狀態、原始證據位置、報告圖表位置。

執行狀態區分未執行、已執行、部分完成；驗收狀態區分待驗證、證據不足、通過、未通過、不適用。規劃完成另記，不代替上述狀態；不適用必須說明原因。缺測不填成零。

| 證據類別 | 必須呈現的內容 |
|---|---|
| 資料 | 各 split 有效完整回合與時數、可用故障前綴、合法 sequences、逐任務 active reward 正例回合；不重複計時或用重疊片段灌大覆蓋 |
| 重建與預測 | 原圖、重建與預測對照、既定基準、指標、實際可比較分母、缺標註或排除原因；64／96-token 對照只支持相同短程更新條件下的觀察 |
| Reward／policy | 逐任務或控制項目的原始計數與指標、基率及 baseline；缺樣本或未定義指標不能視為通過 |
| 系統資源 | DSP 開啟時的推理延遲、deadline misses、整卡取樣顯存峰值與取樣間隔；與關閉 DSP 的訓練量測分開 |
| 閉迴路 | 16 個微任務、7 個背景里程碑與完整成功率，以所有有效回合為分母；另列 active-task 啟用後完成率及其分母 |
| 統計 | 成功與到達率附 Wilson 95% CI；時間在成功或到達者中列 median/IQR，並列未到達數；無成功者時不填假想完成時間 |
| 無效與失敗 | 總嘗試數、無效率、重跑原因、逐回合結果；遊戲失敗與系統無效分開，未完成人工判讀的案例列待分類 |
| 模型比較 | 第二與第三階段使用相同 development manifests，保留配對結果與固定選模依據；final 結果不回流選模，開發勝出不等於統計顯著改善 |

世界模型互動診斷目前待執行，缺此項證據就明列缺項，不當作真實遊戲成功率。原型能執行、正式模型品質合格、研究主張成立分別描述。

## 簡報敘事原型

在時長未知時先建立以下可合併或拆分的段落，不把段落數當成固定頁數。

1. 研究問題與受控遊戲目標，先讓聽眾知道怎樣才算成功。
2. 系統全貌，清楚標示代理只看 RGB 與任務條件，內部狀態由外部系統用於標註及評估。
3. 資料與三階段方法，用同一筆資料走過流程，說明本機限制下的設計選擇。
4. 評估規則，先交代成功率分母、資料隔離、品質 gate 與比較方式。
5. 核心實測證據，挑選支持主張的結果，並保留全部試驗的統計與代表性失敗。
6. 結論與限制，交代最終使用哪個階段、為何選它，以及哪些項目仍待驗證。

簡報縮短時先移出公式推導、超參數細節與額外圖表到備用頁，保留研究問題、實測證據、分母及限制。沒有可用閉迴路模型時，核心證據段改呈現最後完成的階段與停止原因，不以示範影片冒充代理成果。

## 不同結果如何完成報告

- 第二、三階段皆合格：依固定 development 選模規則選擇，報告選定模型的 final 結果；第三階段未改善時如實保留第二階段。
- 第二階段合格、第三階段未啟動或不合格：以第二階段為最終模型，說明第三階段的狀態與原因，不聲稱已驗證三階段整體成效。
- 第二階段未合格或前置 gate 待驗證：呈現截至該階段的實測、阻礙與缺口，不將第二階段包裝成合格退路。
- 最終電磁矩陣成功數為零：仍報告節點到達、有效回合分母、信賴區間及失敗證據；不以局部進度改稱完整成功。

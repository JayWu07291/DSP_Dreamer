## 特定畫面的問題

R004 的 LPIPS 從 0.328765 降到 0.298587，但左上面板及左右下角原本沒有的 UI 仍在。科技樹 R016 從 0.448683 降到 0.436036，僅改善 2.82%，節點結構仍錯。這和使用者覺得沒有明顯改變的觀察一致。

上一輪的四圖上下文實驗已指出，移除歷史並未消除 R001、R004、R016 的錯誤。本輪沒有重做 GPU 推論，僅檢查最新保存的輸出。

## 實際抽樣分布

依本輪 1000 次更新的 `samples` 與 `length`，透過既有 ModelView 讀取 train metadata，核對全部樣本的合法 sequence 起點，統計實際送入 loss 的 384,000 個影格曝光次數，包含重複抽樣。沒有讀取或完整核對 RGB。

- 開局微任務 `task_id=0` 只有 1,335 次曝光，占 **0.348%**。train 有 1,084 張合法模型影格屬於這個微任務。
- `task_id=1` 占 4.517%，但這個 ID 不是科技樹畫面的標籤，不能據此得出科技樹曝光比例。
- 等待狀態 `task_id=16` 占 23.708%，微任務 7 占 17.550%，微任務 13 占 14.084%。三者合計約 55.34%。

目前 A 從全部合法片段起點均勻抽樣，並非各微任務均衡。短暫的開局和回合邊界較少曝光是實際量到的現象，但尚未證明它造成 UI 幻覺，也未證明 task 均衡會改善重建。

## 下一步

後續已完成[問題畫面的抽樣比例檢查](A-screen-sampling-audit.md)。開局 HUD 尚未完整出現的曝光約 0.139%，科技樹約 2.251%；一般遊戲中研究列不可見的畫面約 12.639%。因此抽樣偏差足以支持開局對照，但不能當成所有 UI 錯誤的單一解釋。

先保留本輪權重，暫不再沿原配方追加長訓練。優先核對 train 中開局無 UI、科技樹等畫面的覆蓋與抽樣量，再安排只改抽樣的對照；task ID 只能當粗略分層，不能替代 UI 類型。若覆蓋足夠，再從相同 checkpoint、相同 seed 做遮罩上限 0.9／0.5 的單一變量對照。模型容量、loss 權重、抽樣、遮罩不應一次全改。

判斷要同時看完整 200 圖指標和錯誤 UI／節點結構，不能只挑平均 LPIPS 較低的一組。對照訓練仍由使用者手動執行，本次沒有啟動訓練、修改配方、資料集或帳本。
